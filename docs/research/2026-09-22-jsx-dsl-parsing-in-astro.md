## Question

The repo stores articles as a custom JSX-only DSL (`<Paragraph>`, `<Callout>`, `<YouTube … />`, inline `<Bold>`/`<Link>`), parsed by a hand-rolled tokenizer in `src/blocks/dsl/parser.ts`, rendered by string concatenation in `src/blocks/dsl/renderer.ts`, and round-tripped by `src/blocks/dsl/serializer.ts`. Content lives in `src/content/blog/<slug>/index.mdx` loaded through a `glob` collection, while `mdx()` stays only as a loader per the `astro.config.mjs` comment and ADR-0010; a single `renderDocument` serves both SSG (`src/pages/blog/[...slug].astro`) and SSR preview (`src/pages/admin/posts/[id]/preview.astro`, `export const prerender = false`) on Cloudflare Workers. Given that, what is the most elegant simple-yet-powerful way to parse and process this DSL — keep hardening the hand parser, adopt a real JSX parser, return to an MDX/unified pipeline, store JSON AST instead, or share a grammar with the editor?

## Answer in one paragraph

**Keep the hand parser's architecture and harden it in place; do not adopt a new parsing stack.** The tokenizer-plus-recovery-plus-`inspectDocument` shape is load-bearing and already tested (`src/blocks/dsl/inspect.test.ts`): total recovery on author typos, unknown-tag and schema-mismatch problems, bare-text auto-paragraphing, and inline-mark handling are behaviors a real JSX parser (Babel, acorn) or an MDX pipeline would make you re-implement on top anyway — and both are unforgiving by design where this system must be forgiving. The actual defects are small and local: the `{…}` expression reader is a regex rewrite that corrupts mixed-quote literals and counts braces inside strings, tokens and problems carry no positions, node IDs are non-deterministic (`Date.now()`), and prop interpolation in several block `render` functions bypasses escaping on the exact path that feeds Astro's unescaped `set:html`. Fix those five things with dependency-free code (a ~80-line total literal parser shared by the attribute scanner, offset/line positions on tokens and problems, per-parse deterministic IDs, one `escapeAttr` boundary, serializer round-trip tests), and the current design is sound. The one fallback worth keeping warm is a **Lezer grammar** shared by parser and editor — it is the only alternative that adds a capability the hardened hand parser cannot (incremental re-parsing plus editor-native error nodes) — but only after the lint-via-`inspectDocument` step proves the demand. Everything below grounds that paragraph in the code as read and in primary sources only.

## 1. Current diagnosis (read at this revision)

Files read fully: `src/blocks/dsl/parser.ts` (489 lines), `src/blocks/dsl/renderer.ts` (209), `src/blocks/dsl/serializer.ts` (92), `src/blocks/dsl/index.ts`, `src/blocks/dsl/inspect.test.ts` (90), `src/blocks/types.ts`, `src/blocks/marks.ts`, `src/blocks/insertion.ts`, `src/blocks/registry.ts`, `src/blocks/paragraph/index.ts`, `src/blocks/callout/index.ts`, `src/blocks/youtube/index.ts`, `src/blocks/image/index.ts`, `src/blocks/code/index.ts`, `src/blocks/list/index.ts`, `src/components/article-display.astro`, `src/pages/blog/[...slug].astro`, `src/pages/admin/posts/[id]/preview.astro`, `src/content.config.ts`, `astro.config.mjs`, `package.json`.

### 1.1 How the pipeline works today

`tokenizeDsl` hand-scans `<Tag attr="…" attr={…} />`, `</Tag>`, text, and `<!--…-->` (`parser.ts:62-219`). `inspectDocument` (`parser.ts:283-479`) folds tokens with a block stack plus inline-mark stacks (`MARK_TAG_ALIASES` in `marks.ts`), auto-wraps bare root text in `Paragraph`, validates props with each block's Valibot schema via `v.safeParse`, and reports four problem codes (`unknown-block`, `invalid-props`, `recovered-tag`, `unterminated-comment`) with two severities. `parseDslToBlocks` drops the problems; `renderDocument` (`renderer.ts:160-209`) parses, loads server data, collects JSON-LD, concatenates block HTML, and aggregates styles. `article-display.astro` injects the result with `<Fragment set:html={html} />` (`article-display.astro:34`). What is good about this — total recovery, the inspect/parse split, registry-driven validation — is already recorded in the companion rearchitecture note (§1.1 items 1–2) and is not re-argued here.

### 1.2 Correctness gaps, each pinned to a line

1. **Expression reader is unsound** (`parser.ts:23-53`). `parseJsxExpressionValue` tries `JSON.parse`, then rewrites single-quoted strings and bare keys into JSON with two regexes, else returns the raw string. The single-quote regex `/'([^'\\]*(?:\\.[^'\\]*)*)'/g` matches across double-quoted regions: `{a: "don't stop", b: 'x'}` matches `'t stop", b: '` as a "single-quoted string", `JSON.stringify`s its interior (escaping the real double quotes), and corrupts the object — `JSON.parse` then fails and the whole prop silently becomes the raw string. Any author text with an apostrophe inside a double-quoted value adjacent to a single-quoted value triggers this. The failure mode is silent type-change (object → string), downstream of which `safeParse` reports `invalid-props` against a symptom, not the cause.
2. **Brace counting is string-blind** (`parser.ts:186-196`). The `{…}` scanner counts `{`/`}` without tracking string literals, so `<CodeBlock code={"a}b"} />` closes the expression at the `}` inside the string. Same for template literals, regexes, and apostrophes containing braces. This is the same bug class as gap 1 with a different trigger.
3. **No positions anywhere.** `Token` carries `raw` but no offset; `DocumentProblem` (`parser.ts:262-268`) carries `tagName` and `message` but no line/column/offset. Consequences: error messages cannot say *where*; the planned editor lint (companion note §3.4 item 2) cannot map a problem to a squiggle without re-scanning; misnesting recovery messages (`</${name}> closed … before it was finished`) name tags the author may have typed pages apart.
4. **Non-deterministic IDs** (`parser.ts:240-244`). `generateNodeId` mixes `Date.now().toString(36)` with a module-level counter that never resets. Two parses of one document disagree; parses disagree across processes. This forbids snapshot-testing parsed trees, content-addressing blocks for the projector, and stable decoration keys in the editor (companion note §3.1 fix 1 already names this; it is repeated here because every option below is judged partly on determinism).
5. **Recovery re-parents surprisingly** (`parser.ts:434-454`). On `</X>` with unclosed elements above the match, `stack.splice(matchIdx, 1)` extracts the matched element while leaving the unclosed ones on the stack, and `appendChild` attaches the closed node to the innermost unclosed element — i.e. a "closed" node can end up *inside* a node that textually contains it only partially. Total (never throws) but the tree shape on misnesting is not pinned by any test; `inspect.test.ts` asserts messages, not shapes.
6. **Tag charset is an undocumented subset of JSX** (`parser.ts:118`, `154`). Names allow `[a-zA-Z0-9_-]` only — no `.` or `:`. Real JSX member expressions such as `<myComponents.thisOne />` (legal per the MDX syntax docs, §2 P2 below) tokenize as tag `myComponents` followed by junk text. Acceptable for a DSL, but the boundary is nowhere stated and the failure presents as `unknown-block` + stray text rather than one clear error.
7. **Comment handling swallows silently except via callback** (`parser.ts:85-99`). `<!--` without `-->` consumes the rest of the document; only callers passing `report` learn about it — `parseDslToBlocks` does not pass one, so the renderer silently drops content. (The `inspectDocument` path does surface it; the direct render path is what preview and production use.)

### 1.3 Escaping gaps (the trust-boundary bug class)

`article-display.astro:34` uses `set:html`, and Astro's own directive reference warns in bold: "**The value is not automatically escaped by Astro!** Be sure that you trust the value, or that you have escaped it manually" ([directives reference](https://docs.astro.build/en/reference/directives-reference/#sethtml), read 2026-09-22). So `renderDocument`'s output string is the trust boundary, and these paths cross it unescaped:

- `renderer.ts:16-20` `escapeHtml` covers `& < >` only — correct for text nodes, insufficient for attribute values (no `"`/`'` encoding). OWASP's rule for attribute contexts is explicit: apply HTML attribute encoding *and* always quote attributes ([XSS Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html), read 2026-09-22).
- `youtube/index.ts:37-45` interpolates `props.id` into `src="…/embed/${props.id}"` and `props.title` into `title="…"` raw; `image/index.ts:27-30` interpolates `src`, `alt`, `caption`, `stretch` raw; `callout/index.ts:49-57` interpolates `title`, `stretch`, `props.class` raw; `list/index.ts:41-46` interpolates `listStyle` into a `style="…"` attribute (a CSS context — OWASP lists inline-style placement as a context needing its own encoding) and `start` raw. Props are Valibot-validated as strings, but a string schema does not make `"><script>` safe.
- `code/index.ts` is the counterexample that proves the rule: it escapes `title` and body (`code/index.ts:12-19,36`) but not `lang` in `data-lang="…"` / `language-…` (`code/index.ts:41`).
- `renderer.ts:77-85`: when a block mixes block children with inline spans, the spans render via bare `escapeHtml(text)` — marks and link `markDefs` are silently dropped (asymmetric with the inline-only branch at `renderer.ts:73-75`).
- `serializer.ts:5-13` escapes `"` as `\"` (JS-string style). The parser's quoted scanner (`parser.ts:176-184`) preserves the backslash literally, so serialize→parse drifts (`"` becomes `\"` in the value). The two modules disagree on the attribute-value codec and no round-trip test pins it.

Threat-model honesty: authors are two trusted editors, so this is stored-self-XSS at worst, not a public input hole — but the preview route is SSR on Workers and drafts persist in D1, so a pasted third-party snippet (YouTube title, image alt, affiliate `amazon-product` props) with a quote-breakout persists and renders unescaped for every reader. Fix-before-elegance, as the companion note's Phase 0 already orders it.

### 1.4 Complexity and coverage costs

- One 489-line file owns tokenizing, expression evaluation, ID generation, validation orchestration, recovery, and problem reporting. The expression sub-language alone re-invents a JSON5-subset evaluator with regexes.
- `inspect.test.ts` has 9 tests: clean doc, unknown block, invalid props, unclosed tag, stray close, unterminated comment, recovery totality, plus two registry-snippet sweeps. There are **zero** tests for: expression values (numbers, booleans, objects, quote mixes), brace-in-string, determinism, positions, recovery tree *shapes*, renderer escaping, serializer round-trips. `editor-model.test.ts` and `insertion.test.ts` cover adjacent seams, not the parser core.
- Runtime cost today is ~zero dependencies (Valibot only, tree-shaken and dependency-free per its intro, [valibot.dev](https://valibot.dev/guides/introduction/), read 2026-09-22) — any option that adds a parser library must justify itself against this, because the SSR preview pays its parse cost per request inside Workers CPU limits (§2 P4).

## 2. Principles (primary sources only; all read 2026-09-22)

**P1 — Build-time content wants a loader plus a schema; live content is a different kind with explicit costs.** Astro collections require a `loader` (here `glob({ base, pattern })`) with an optional `schema`, queried via `getCollection()`/`getEntry()` and rendered via `render()` to a `<Content/>` component; live collections instead "fetch their data at runtime" with listed limitations: "**No MDX support**: MDX cannot be rendered at runtime", "No image optimization", "Performance considerations", "No data store persistence" ([content collections](https://docs.astro.build/en/guides/content-collections/), read 2026-09-22). Consequence: the single-string-renderer behind Article Display is not a hack but the correct adaptation — keep published reads on the build-time collection, keep DSL strings out of any "live MDX" idea.

**P2 — MDX is an odd mix: forgiving markdown crossed with unforgiving JavaScript.** "Markdown is **whitespace sensitive** and **forgiving** (what you type may not exactly work but it won't crash) whereas JavaScript is **whitespace insensitive** and **unforgiving** (it does crash on typos)"; deviations are documented: indented code doesn't work, autolinks don't work (they can be "indistinguishable from JSX (for example: `<svg:rect>`)"), HTML must be JSX (`<img>` → `<img />`), unescaped `<`/`{` must be escaped; components must be defined and `<myComponents.thisOne />` member expressions are legal ([what-is-mdx](https://mdxjs.com/docs/what-is-mdx/), modified 2025-01-27, read 2026-09-22). Consequence: "JSX-only, no Markdown" is strictly simpler than MDX (no interleaving rules like same-line-vs-separate-line blocks), *provided* the parser stays total — which is exactly what the hand parser buys and what any real-JSX-parser option must re-add by hand.

**P3 — `@astrojs/mdx` 8.0.1 is a build-time compiler, and keeping it as a loader is coherent.** The integration page (v8.0.1 header) documents `loader: glob({ pattern: "**/*.{md,mdx}" })` collections, `render()` yielding `<Content/>`, frontmatter support, and the `components` prop for mapping elements to custom components ([MDX integration](https://docs.astro.build/en/guides/integrations-guide/mdx/), read 2026-09-22). Nothing on that page renders at request time. Consequence: `mdx()` as loader-only (current `astro.config.mjs`) is a legitimate configuration — the `.mdx` extension buys glob loading plus frontmatter; the DSL body never needs the MDX compiler. Removing the integration would require renaming bundles or a custom loader; keeping it costs one dev-time integration that never runs at SSR.

**P4 — `set:html` is an explicit trust boundary; on-demand routes run on workerd.** Astro: `set:html` values are "not automatically escaped" (P1 §1.3 link); on-demand rendering needs an adapter, per-page `export const prerender = false`, and "runs your project on a specific runtime" ([on-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/), read 2026-09-22). The Cloudflare adapter page (`@astrojs/cloudflare` v14.3.2 header) documents `imageService: 'compile'` (this repo's setting), `prerenderEnvironment` defaulting to `'workerd'`, `nodejs_compat` for `node:*` imports, and that "the new workerd environment does not support CommonJS syntax, including… `require` and `module.exports`" ([Cloudflare adapter](https://docs.astro.build/en/guides/integrations-guide/cloudflare/), read 2026-09-22); static-asset routing falls back to the Worker when no file matches ([adapter page](https://docs.astro.build/en/guides/integrations-guide/cloudflare/)). Workers limits (updated 2026-09-05): Free 10 ms CPU / Paid 30 s default up to 5 min, 128 MB per isolate, 64 MiB uncompressed Worker size, 1 s startup budget ([limits](https://developers.cloudflare.com/workers/platform/limits/), read 2026-09-22). Consequence: SSG and SSR preview execute the *same* `renderDocument` in Node and in workerd respectively — build-vs-runtime parity is a property of sharing the module, and any new dependency must be ESM, workerd-safe, and small enough to never threaten the 1 s startup or per-request CPU on the preview path.

**P5 — Output encoding is per-context, not one function.** OWASP: HTML-body encoding (`& < > " '`), attribute encoding plus mandatory quoting, URL encoding before attribute encoding for `href`/`src`, separate CSS/JS encodings, and a list of safe sinks (`.textContent`, `setAttribute` with hardcoded names); dangerous contexts (inline event handlers, `style` URLs, `javascript:` URLs) must not receive variables at all ([XSS Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)). Consequence: the fix is one `escapeAttr` used at every `"`-quoted interpolation plus an `href` allowlist (`http(s):`, `/`, `#`) — not a sanitizer dependency (no raw HTML is ever accepted, so DOMPurify-class sanitization answers a question this DSL never asks).

**P6 — Real JSX parsers: what each one actually offers.** `@babel/parser` supports `jsx`/`typescript` plugins, `errorRecovery: true` (collecting into `ast.errors`), `loc`/`ranges`, and structured `code`/`reasonCode` errors ([babel-parser docs](https://babeljs.io/docs/babel-parser), read 2026-09-22); npm unpacked size 7.29.9 ≈ **2.0 MB**. `acorn` + `acorn-jsx` is the plugin pattern `acorn.Parser.extend(jsx()).parse(…)` with `allowNamespaces`/`allowNamespacedObjects` options ([acorn-jsx repo](https://github.com/acornjs/acorn-jsx), read 2026-09-22); unpacked acorn 8.18.0 ≈ **565 KB** + acorn-jsx 5.3.2 ≈ **24 KB**. TypeScript's compiler API offers `ts.createSourceFile(fileName, sourceText, scriptTarget, setParentNodes)` plus `getLineAndCharacterOfPosition` and `forEachChild` traversal ([Using the Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API), read 2026-09-22); unpacked typescript 7.0.2 ≈ **2.5 MB** — and the repo already depends on it, but as a build-time dev tool, not a runtime bundle member. `sucrase` is disqualified by its own README: "Sucrase does not check your code for errors… If you give it invalid code, it might produce invalid code… Always use Sucrase with a linter or typechecker" ([sucrase repo](https://github.com/alangpierce/sucrase), read 2026-09-22) — a transformer that may miscompile invalid input is the opposite of what an author-typo-tolerant CMS parser needs. `htmlparser2` is "the fast & forgiving HTML/XML parser" with a callback interface, `xmlMode` (self-closing, CDATA), `lowerCaseTags`, and `withStartIndices`/`withEndIndices` DOM options ([htmlparser2 repo](https://github.com/fb55/htmlparser2), read 2026-09-22); unpacked 12.0.0 ≈ **235 KB** — forgiving like the hand parser, but HTML semantics (implied tags, entity decoding) rather than JSX semantics (`{…}` expressions are opaque to it).
